# Task: Fix verified detection-algorithm bugs in the Shade Sayer firmware

You are working in the `shade_sayer` repository: ESP32-S3 firmware (ESP-IDF, C++17)
for a handheld color-identification device for visually-impaired quilters. A TCS3530
XYZ color sensor reads a fabric swatch; the pipeline corrects the raw reading
(gain/integration normalization → black-level subtraction → D65 scaling → polynomial
color correction matrix "PCCM" → IR compensation → Lab conversion → lightness/
saturation correction), then matches the resulting Lab value against reference
tables using CIEDE2000 (ΔE2000) and speaks the color name.

Two matchers exist:
- **Kona matcher** (`main/konaref.cpp`, table generated by
  `scripts/generate_kona_table.py` from `kona_captures.json`, 365 entries): matched
  against `result->scan_lab`.
- **xkcd fallback matcher** (`main/color_matcher.cpp` + `main/color_database.cpp`,
  949 entries, VP-tree in `main/vptree_data.h` generated by
  `scripts/generate_vptree.py`): matched against `result->corrected_lab`.

Auto-calibration (`main/auto_calibrate.cpp`) collects reference-swatch measurements
and runs an Adam optimizer over the PCCM and scalar parameters
(`color_calib_params_t`), persisting results to NVS; `main/color_pipeline.cpp`
loads and applies them at runtime.

The code also builds on a host PC: `host/CMakeLists.txt` compiles the core sources
natively (stub glue in `main/tcs_glue.{h,cpp}`, guard macro `TCS_HOST_BUILD=1`,
ESP-only sections behind `#ifdef ESP_PLATFORM`). Host tests live in `tests/host/`.

A code review verified the bugs below (empirical evidence included). Implement the
fixes. **Line numbers are from the review and may have drifted — locate code by the
quoted symbols/snippets, not by line number.** Match the existing code style
(Allman braces, ESP_LOG/TCS_LOG logging, doc comments). Keep both the ESP-IDF
build and the host build compiling.

## Required fixes (in priority order)

### Fix 1 — VP-tree nearest-neighbor search is unsound because CIEDE2000 is not a metric

**Where:** `vptree_search_recursive()` in `main/color_matcher.cpp`,
`kona_vp_search()` in `main/konaref.cpp`, and the tree generators
`scripts/generate_vptree.py` and the VP-tree section of
`scripts/generate_kona_table.py`.

**Reasoning:** VP-tree pruning (`dist + best_distance > median` to enter the far
subtree, `dist - best_distance <= median` to enter the near subtree) is derived
from the triangle inequality. CIEDE2000 violates the triangle inequality (its hue
rotation term RT and the S-weightings break metricity), so the pruning can discard
the subtree containing the true nearest neighbor. The pruning derivation itself is
correct; the premise (metric distance) is false.

**Empirical evidence (host harness, tree search vs. brute-force linear scan):**
- xkcd tree, Lab grid sweep (L 2.5–100, a/b −90..90): 159/4096 queries (3.9%)
  returned a non-nearest color, worst gap 6.1 ΔE. Example: query
  Lab(2.5,−18,−54) → tree returns "Prussian Blue" at ΔE 23.5, true nearest is
  "Dark Blue Grey" at ΔE 21.1.
- Kona tree, realistic queries (each of the 365 entries + uniform ±3 noise on
  L/a/b, 30 reps): 5/10,950 wrong swatch IDs including 1 accept-threshold flip
  (linear ΔE < 5.0 would accept, tree ΔE ≥ 5.0 rejects). So ~1 in 2000 real scans
  names the wrong swatch or wrongly reports no match, and error rates climb
  sharply for colors far from the database (dark/saturated regions — exactly where
  an uncalibrated unit lands).

**Fix (chosen approach — replace tree search with linear scan):** With only 365
and 949 entries, a full linear CIEDE2000 scan is on the order of a millisecond on
the ESP32-S3 and is exactly correct.
- In `color_matcher_find_closest()`: drop the VP-tree traversal and use the
  existing linear scan `find_closest_color_lab()` (in `main/color_database.cpp`)
  unconditionally. Keep the statistics counters coherent. Remove or neutralize the
  now-dead VP-tree code paths and the tree/database count-mismatch warning in
  `color_matcher_init()` (see Fix 8 — that hazard disappears with the tree).
- In `kona_ref_find_closest()` (`main/konaref.cpp`): the linear-scan fallback is
  already written below the VP-tree branch. Delete the VP-tree branch and always
  use the linear scan.
- Do not regenerate or hand-edit the generated data files; simply stop consuming
  the tree data. (Optionally remove tree emission from the generators, but the
  firmware change is what matters.)

An acceptable alternative (only if you have a strong reason): keep a tree built on
**Euclidean Lab distance** (a true metric), collect top-k candidates, then re-rank
those k with CIEDE2000. Do NOT keep CIEDE2000 as the tree metric with a heuristic
slack factor — no finite slack is provably sufficient.

**Acceptance:** for any Lab query, the returned entry and ΔE must equal the
brute-force minimum over the table (bit-for-bit the same `color_math_delta_e_ciede2000`
calls). A host test comparing against brute force over a Lab grid must show 0
mismatches.

### Fix 2 — Calibrated `lightness_offset` is zeroed on NVS load but not on direct apply

**Where:** `color_pipeline_init()` in `main/color_pipeline.cpp` — the NVS load
path contains `loaded_params.lightness_offset = 0.0f;` immediately after a
successful `tcs_storage_load_blob("auto_cal", "params", ...)` — versus
`color_pipeline_set_params()` in the same file, which zeroes `pccm[i][9]` but
does **not** zero `lightness_offset`.

**Reasoning:** Right after calibration completes, `auto_cal_apply_results()` →
`color_pipeline_set_params()` installs the optimizer's `lightness_offset`
(constraint range ±50; simulations found optima around −6.4). After the next
reboot, the NVS load path silently zeroes it. The device's lightness mapping
therefore shifts by several L* units across a reboot — same stored calibration,
different behavior. Worse, the log line just after the zeroing prints
`loaded_params.lightness_offset` (already zeroed), hiding the discrepancy. The
optimizer also actively tunes this parameter (gradient + Adam update in
`auto_calibrate.cpp`), so it must not be discarded by one consumer only.

**Fix:** Make the two paths consistent. The offset is a legitimate optimized
parameter, so **honor it in both paths**: delete the
`loaded_params.lightness_offset = 0.0f;` line from the NVS load path. Also mirror
the `pccm[i][9] = 0` clearing into the NVS load path so both paths sanitize the
same fields the same way (note `apply_constraints()` in `auto_calibrate.cpp`
already forces `pccm[i][9]` to 0 before save, so this is belt-and-braces).
Update the misleading comment in `color_pipeline_set_params()` that says "see NVS
load path for full explanation" (the load path never explained it).

**Acceptance:** loading params from NVS and applying the identical struct via
`color_pipeline_set_params()` must leave `s_params` in an identical state.

### Fix 3 — Calibrated saturation parameters are never used at runtime

**Where:** `color_pipeline_process_xyz()` in `main/color_pipeline.cpp` calls
`color_math_enhance_saturation(&result->lab, s_config.gray_threshold,
s_config.color_threshold, s_config.saturation_boost)` — and the later
confidence-scaled re-boost block also reads `s_config.saturation_boost`.

**Reasoning:** Auto-calibration optimizes `s_params.saturation_boost` (and carries
`s_params.gray_threshold` / `s_params.color_threshold`), saves them to NVS, loads
them, and even logs them — but the pipeline reads the fixed firmware defaults from
`s_config` (boost 1.5, gray 5.0, color 60.0) instead. The optimizer's objective
includes its own boost value (see `apply_calibration()` step 6 in
`auto_calibrate.cpp`), so the fitted PCCM implicitly compensates for a boost the
runtime never applies with that value. The two structs also disagree at rest
(config gray_threshold 5.0 vs params 4.0).

**Fix:** In `color_pipeline_process_xyz()` (both the initial boost and the
confidence-scaled re-boost), source `saturation_boost`, `gray_threshold`, and
`color_threshold` from `s_params` instead of `s_config`. Audit remaining uses of
the duplicated fields in `s_config` and either remove them or document that they
are defaults used only until calibration params exist.

**Acceptance:** after `color_pipeline_set_params()` with a distinctive
`saturation_boost` (e.g. 2.0), the enhancement applied in `process_xyz` must use
that value (observable via the debug log line or a host unit test).

### Fix 4 — Calibration optimizer objective is computed in a different color space than the matcher uses

**Where:** `apply_calibration()` in `main/auto_calibrate.cpp` (its doc comment
claims it "EXACTLY" matches the runtime pipeline) versus the matching path in
`color_pipeline_process_xyz()`.

**Reasoning:** The Kona matcher consumes `result->scan_lab`, which is deliberately
computed **without** saturation boost and without the Z display floor (a long
comment in `process_xyz` explains that boost+clamp collapses saturated swatches
like CARROT/TORCH into identical values). The xkcd fallback consumes
`corrected_lab` — also unboosted. But `apply_calibration()` applies
`color_math_enhance_saturation(...)` before computing ΔE against the calibration
targets, and it also omits the runtime's Y-normalization step (runtime scales XYZ
proportionally when Y > D65_Y before Lab conversion). So the optimizer minimizes
error in (approximately) the *display* space while matching happens in the *scan*
space: the optimizer can satisfy a chroma target by "spending" saturation boost
instead of fixing the PCCM, leaving the matcher with under-corrected chroma.

**Fix:** Make `apply_calibration()` mirror the scan/matching path:
1. Remove the `color_math_enhance_saturation(...)` call from `apply_calibration()`.
2. Add the Y-normalization step before Lab conversion: if `corrected_xyz.y > D65_Y`,
   scale x/y/z by `D65_Y / corrected_xyz.y` (same as the runtime block commented
   "Normalize XYZ values when luminance exceeds D65 white reference").
3. Keep lightness correction with `lightness_scale = 1.0f` in the temp params
   (that part already matches the scan path).
4. Update `init_ccm_from_measurements()` accordingly: its target-inversion
   currently divides a\*/b\* by `saturation_boost` to "undo" the boost — remove
   that division since the objective no longer includes boost.
5. Update the doc comment to state precisely which runtime path it mirrors
   (the scan/matching path, not the display path).

Note: with the boost removed from the objective, the gradient for
`saturation_boost` will be ~0 and Adam will leave it near its start value. That is
acceptable; boost remains a display-only cosmetic parameter. If you prefer, stop
optimizing it entirely (skip its gradient/update like the PCCM constant term is
skipped).

**Acceptance:** for identical input XYZ and params, `apply_calibration()` must
produce the same Lab as the runtime `scan_lab` computation (host test: feed one
XYZ through `color_pipeline_process_xyz` and through `apply_calibration` with the
same params; compare `result->scan_lab` to the returned Lab within float epsilon).
The existing `MAX_GRADIENT_MAGNITUDE` clamp can remain.

### Fix 5 — IR compensation is not modeled in calibration

**Where:** Runtime `apply_sensor_correction()` in `main/color_pipeline.cpp`
subtracts IR crosstalk after the PCCM (block starting
`if (reading->ir > 0 && reading->clear > 0 ...`, LED coefficients
{0.35, 0.25, 0.05}). The calibration flow in `main/main.cpp` (search for
`auto_cal_submit_measurement`) submits only RESP-normalized XYZ; `apply_calibration()`
never subtracts IR.

**Reasoning:** Parameters are fit to a pipeline without IR subtraction but executed
in a pipeline with IR subtraction. Calibration measurements are taken with the LED
on (nonzero IR), so this is a systematic bias between calibration and use.

**Fix (choose the minimal-risk option):** subtract IR at measurement-submission
time in `main.cpp` so the optimizer sees IR-free data consistent with what the
runtime PCCM effectively receives. Concretely, in the calibration measurement
block in `main.cpp`: compute `resp_ir = reading.ir / (TCS3530_RESP_Y *
gain_multiplier * integration_scale)` and, mirroring the runtime coefficients and
interpolation (`clear/ir` ratio → t; with LED on this is normally t=1 → LED
coefficients), subtract `resp_ir * coeff_{x,y,z}` from `resp_x/resp_y/resp_z`,
clamping at ≥ 0, before building the submitted `xyz_t`. Factor the coefficient
lookup/interpolation into a small shared helper (e.g. in `color_math` or
`color_pipeline`) so runtime and calibration use one implementation — do not
duplicate the constants.

Caveat to preserve: the runtime applies IR subtraction *after* the PCCM in the
XYZ output domain while this fix subtracts *before*; document the residual
approximation in a comment. (An exact alternative — extending
`cal_measurement_t` to store IR/clear and applying compensation inside
`apply_calibration` post-PCCM exactly as the runtime does — is also acceptable if
you keep it consistent with `apply_sensor_correction`.)

**Acceptance:** calibration and runtime derive their IR coefficients from the same
shared code; a comment documents the domain approximation if the pre-PCCM option
was chosen.

### Fix 6 — Calibration captures a single, unchecked sensor sample

**Where:** the calibration measurement loop in `main/main.cpp` (around the
`s_sensor->measure(&reading)` call between `setLed(true)`/`setLed(false)`).

**Reasoning:** Actual color scans use `capture_averaged_xyz()` (5-sample capture,
saturation rejection, trimmed mean). Calibration — which defines the parameters
every later scan depends on — takes ONE raw `measure()` and never checks
`reading.saturated`. A saturated or noisy white reference silently corrupts the
whole calibration (white is the exposure anchor with 1.5× optimizer weight).

**Fix:** In the calibration loop, take multiple samples (reuse the pattern or the
sample-count config from the pipeline: N=5 with a short delay between samples),
discard samples with `reading.saturated`, and average the RESP-normalized XYZ of
the accepted samples (a trimmed mean as in `capture_averaged_xyz` is ideal; a
plain mean of non-saturated samples is acceptable). If **all** samples are
saturated or the read fails, do not submit: announce via `tts_speak` that the
measurement failed/saturated and loop back so the user can retry the same
reference (the existing `continue` pattern for read failure shows how).
Note `capture_averaged_xyz` itself returns pipeline-corrected XYZ (post-PCCM), so
it cannot be called directly for calibration input — replicate the
multi-sample/reject/average logic on the RESP-normalized values instead, or
refactor a shared raw-averaging helper.

**Acceptance:** a saturated reference can no longer be silently accepted into the
optimizer; the user is prompted to retry.

### Fix 7 — Material auto-detect variance heuristic compares incompatible units

**Where:** `color_math_classify_material()` in `main/color_math.cpp`
(`variance_score = mean_variance / y_norm;`) and its caller wiring in
`main/color_pipeline.cpp` (`s_capture_variance` = stddev² of **corrected** XYZ,
0–100 domain; `reading->y` = raw ADC counts, magnitude 10³–10⁶).

**Reasoning:** The score divides a 0–100-domain variance by a raw count, yielding
~0 always; the fabric threshold (0.05) can never trigger, so variance-based fabric
detection is dead. Similarly `clear_ratio = clear / (x+y+z)` compares raw
wideband clear counts against raw X+Y+Z without responsivity normalization, making
the metal (>1.5) and plastic (>1.2) thresholds essentially arbitrary; combined
with the final `return MATERIAL_FABRIC` fallback, the METAL/PLASTIC branches are
nearly unreachable. (Latent: `auto_detect_material` defaults off, but the feature
is dead-on-arrival if enabled.)

**Fix:** Make the variance score dimensionally consistent: compute a coefficient
of variation in ONE domain. Simplest: change the classifier interface/caller so
the variance and the mean it is normalized by come from the same corrected-XYZ
statistics — e.g. pass the capture `mean_xyz` alongside `s_capture_variance` and
use `sqrt(mean_variance) / mean_y` (CoV of corrected Y). Retune the threshold to
match (the pipeline already uses `TEXTURE_CV_THRESHOLD = 0.15f` for CoV of
corrected Y — reuse that constant or derive from it). For the clear-ratio tests,
normalize channels by their responsivities before ratioing
(`clear`/RESP vs sum of X/RESP_X + Y/RESP_Y + Z/RESP_Z) and add a comment that the
metal/plastic thresholds are provisional pending real measurements. Keep the
fabric default fallback (it is the primary use case) but log at INFO when the
classifier falls through.

**Acceptance:** with plausible synthetic inputs (corrected-XYZ variance CoV of
0.3 on Y), the classifier must return MATERIAL_FABRIC via the variance branch,
not via the fallback. Add a host unit test.

### Fix 8 — VP-tree search uses an unchecked DB lookup (uninitialized Lab on mismatch)

**Where:** `vptree_search_recursive()` in `main/color_matcher.cpp`:
`color_database_get_entry((uint32_t)node->color_index, NULL, 0, &node_lab);` —
return value ignored — and `color_matcher_init()` which logs the tree/database
count mismatch as a warning and continues ("This is not fatal").

**Reasoning:** If the generated tree and the database ever disagree (the init code
explicitly tolerates this), an out-of-range `color_index` leaves `node_lab`
uninitialized; garbage distances then steer both the best-match update and the
pruning nondeterministically.

**Fix:** If Fix 1 removed the VP-tree path entirely, this disappears — just make
`color_matcher_init()` fail (or permanently select linear search) on count
mismatch instead of warning. If any tree code is retained, check the
`color_database_get_entry` return value and skip the node (or abort to linear
search) on failure.

### Fix 9 — `auto_cal_submit_measurements_from_file` can attribute measurements to the wrong reference

**Where:** `auto_cal_submit_measurements_from_file()` in `main/auto_calibrate.cpp`.

**Reasoning:** The function name-matches each file line against `references[i]`,
but then calls `auto_cal_submit_measurement()`, which always stores at
`status.current_ref_index` — the found index `i` is only used as a gate. If file
lines are out of order relative to the reference sequence (or a name appears
twice), measurements are silently attributed to the wrong swatches. The sibling
function `auto_cal_submit_raw_measurements_from_file()` guards correctly by
comparing against `auto_cal_get_current_ref_name()`.

**Fix:** Mirror the raw variant's guard: only submit when the line's name equals
the *current* reference's name; otherwise log a warning and skip the line. (Do
not add an API to submit at an arbitrary index — keep the sequential invariant.)

**Acceptance:** a file with lines in shuffled order must only apply the lines
matching the current reference sequence position, warning on the rest.

### Fix 10 — Optimizer early-exit aborts on a single flat iteration

**Where:** end of the optimization loop in `auto_cal_run_optimization()`
(`main/auto_calibrate.cpp`):
`if (improvement < MIN_IMPROVEMENT && improvement >= 0) { ... break; }`.

**Reasoning:** Adam is momentum-based; single near-zero-improvement iterations are
routine while the moment estimates warm up or when traversing a plateau. Breaking
on the FIRST flat iteration (a) is not evidence of convergence and (b) bypasses
the `stall_count` / warm-restart machinery entirely (one flat iteration is far
more likely than `MAX_STALL_ITERATIONS`=100 consecutive non-improving ones),
making the warm restart near-dead code.

**Fix:** Track consecutive sub-`MIN_IMPROVEMENT` iterations and only break after a
meaningful run of them (e.g. a new counter with threshold ~25, reset whenever
`improvement >= MIN_IMPROVEMENT` or a warm restart fires), or delete this check
and rely solely on the existing stall/warm-restart logic. Keep the
`TARGET_DELTA_E` convergence exit as-is.

**Acceptance:** an iteration sequence with one flat step followed by improving
steps must not terminate the loop (host-testable via `autocal_host_test`).

### Fix 11 — Low-light gate double-compensates for `lightness_scale`

**Where:** `color_pipeline_process_xyz()` in `main/color_pipeline.cpp`:
`float effective_min_luminance = s_config.min_luminance * fmaxf(s_params.lightness_scale, 0.01f);`

**Reasoning:** The corrected L\* being compared already includes
`lightness_scale` — it was applied in linear XYZ space inside
`apply_sensor_correction()` (the code carefully sets `lightness_scale = 1.0f` in
the Lab-space correction precisely to avoid double-scaling). Multiplying the
threshold by the same factor again makes the low-light cutoff depend on
calibration gain in the wrong direction: with a small calibrated scale (e.g.
0.13) the threshold drops to ~0.65 L\*, effectively disabling low-light
detection; with scale > 1 it becomes over-aggressive.

**Fix:** Compare against `s_config.min_luminance` directly:
`result->low_light = result->lab.l < s_config.min_luminance;`. Update the
adjacent debug log line accordingly.

**Acceptance:** the low-light decision for a given corrected L\* is independent of
`lightness_scale`.
